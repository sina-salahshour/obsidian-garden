# Publish your own Obsidian vault

A fork-and-go guide: turn your Obsidian vault into a fast, server-rendered blog with this repo and deploy it to
Vercel (or anywhere Nitro can run).

## What you get

- Your Obsidian notes published as a blog with server-side rendering and streamed sections.
- Courses / series from folders of numbered notes, each with a cover.
- A note graph, full-text search and a command palette.
- Private notes that stay hidden from visitors, and notes that are never published at all.
- Mermaid diagrams, callouts, wikilinks, embeds, footnotes, math (KaTeX) and highlighted code.
- Light and dark themes.

The repo never reads your vault at build time. A one-way sync script copies publishable notes into `content/` and
attachments into `public/attachments/`; you commit those and the host builds from them.

## Prerequisites

- **Node 24** (`engines.node` is `24.x`).
- **pnpm 12.15.0**, the version pinned in `package.json` (`devEngines.packageManager`). Get it through corepack:
  `corepack enable` (corepack ships with Node), then `corepack pnpm@12.15.0 install` or just `pnpm install`.
  `devEngines` is set to `onFail: "download"`, so pnpm fetches the pinned version when it differs.
- **Vite+ (`vp`)**. The `vite-plus` package is a dev dependency, so after install `node_modules/.bin/vp` exists and
  `pnpm dev` / `pnpm build` already use it. The global `vp` CLI is optional but convenient (`vp check`, `vp test`). The
  official install line, from `node_modules/vite-plus/docs/guide/index.md`:

  ```sh
  curl -fsSL https://vite.plus | bash
  ```

  (Windows: `irm https://vite.plus/ps1 | iex`.) Then open a new shell and run `vp help`. Without a global install,
  run it as `pnpm exec vp check`.

- **Git** and a **GitHub** account.
- A **Vercel** account (for the primary deploy path).

## 1. Fork or clone, then install

Fork the repo on GitHub (or clone it and push to a new repo of your own), then:

```sh
git clone <your-fork-url> obsidian-blog
cd obsidian-blog
pnpm install      # or: vp install
```

Keep the repo next to your vault, for example:

```text
~/notes/obsidian        <- your vault
~/notes/obsidian-blog   <- this repo
```

## 2. Make it yours

1. Describe the site in your vault, not in code: copy `docs/vault-starter/_site/` into your vault and edit
   `Site.md` (`site: settings`: title, description, url, locale, social image) and the author note
   (`site: author`). The sync aggregates every note with a `site:` key into `content/site.json`; see "Site notes
   and SEO" in §5. `src/site.config.ts` only holds the fallbacks used when no site note sets a field.

2. Replace `public/favicon.svg` and `public/og.png` (the social preview image) with your own.
3. Remove the author's content. `content/` and `public/attachments/` are generated by the sync, which is a mirror: it
   writes every publishable note and every attachment those notes use, and deletes any file in those two folders that
   your vault does not produce. So the first `pnpm sync` against your vault replaces the example content on its own.
   If you want a clean slate first (for example to preview an empty site), delete the contents of both folders:

   ```sh
   rm -rf content/* public/attachments/*
   ```

## 3. Point it at your vault

The sync reads the vault from `OBSIDIAN_VAULT`, which defaults to `../obsidian` (relative to the repo root).

- Vault is a sibling folder named `obsidian`: nothing to configure.
- Anywhere else:

  ```sh
  OBSIDIAN_VAULT=/path/to/vault pnpm sync
  ```

Commands:

| Command               | What it does                                      |
| --------------------- | ------------------------------------------------- |
| `pnpm sync`           | One sync run                                      |
| `pnpm sync:watch`     | Sync, then re-sync whenever the vault changes     |
| `pnpm sync --dry-run` | Report what would change without writing anything |

The sync never writes to your vault. Vault folders whose names start with `.` (such as `.obsidian`) and folders named
`templates`, `_templates` or `node_modules` are skipped. Notes are `.md` and `.mdx`; attachments are images (png, jpg,
gif, webp, avif, bmp, svg, ico), PDF, audio (mp3, wav, m4a, ogg, flac) and video (webm, mp4, mov, mkv, ogv). Only
attachments that a published note actually references (embeds, images, or the frontmatter `cover` / `image` /
`banner`) are copied.

(`node scripts/sync-vault.ts --dry-run` is the underlying command.)

The summary line looks like:

```text
sync: 3 added, 1 updated, 0 removed, 2 unpublished, 1 private, attachments 2+ 0~ 0-
```

- `added` / `updated` / `removed`: files written to, changed in, or deleted from `content/`.
- `unpublished`: notes skipped because they are never published (`publish: false`, `draft: true`, `.nopublish`).
- `private`: notes synced under `content/_private/`.
- `attachments N+ N~ N-`: attachments added, updated, removed in `public/attachments/`.
- `!` lines below it are warnings (see Troubleshooting). With `--dry-run` the line starts with `[dry-run]`.

If the sync cannot find the vault it stops with `vault not found: <path> (set OBSIDIAN_VAULT)`.

When a note has no `date` or `created`, the sync adds `created:` to the copy in `content/` from the file time. Your
vault file is untouched. `%%comments%%` are stripped from the copy.

## 4. Recommended Obsidian settings

In Obsidian, **Settings -> Files and links**:

- **Use [[Wikilinks]]**: on.
- **New link format**: _Shortest path when possible_.
- **Default location for new attachments**: _Same folder as current file_ (or a subfolder of it).

Attachments are resolved Obsidian-style: the file in the same folder as the note comes first, then the nearest one,
then a file with a unique name. So each folder can have its own `cover.svg`. The sync warns when a name is
ambiguous.

Other things worth knowing:

- Use **Properties** (frontmatter) at the top of a note for `title`, `description`, `tags`, `cover` and visibility.
- Optional: a **Folder notes** community plugin. The convention the site understands is `<folder>/<folder>.md`.

## 5. Writing conventions

The full reference is the starter kit's [Writing Guide](vault-starter/_authoring/Writing%20Guide.md). The short
version:

**Frontmatter** (all optional):

```yaml
---
title: Else the first "# H1", else the filename without its number prefix
description: One sentence for cards, search and SEO
date: 2025-01-31 # or `created`
updated: 2025-02-14 # or `modified`
tags: [topic]
aliases: [Other name]
cover: cover.svg # or image / banner
visibility: private
author: Your Name # a name, alias or [[wikilink]] to an author note
social-image: share.png # raster, ~1200x630 (social sites do not render SVG)
noindex: true # published but hidden from search engines
canonical: https://other.site/post # only for cross-posts
schema: TechArticle # Article | BlogPosting | TechArticle
level: beginner # beginner | intermediate | advanced
---
```

**Visibility**

| Want                                                 | Do                                                                               |
| ---------------------------------------------------- | -------------------------------------------------------------------------------- |
| Public (default)                                     | Nothing                                                                          |
| Private note (synced, committed, hidden on the site) | `visibility: private`, or `private: true`, or tag `#private`                     |
| Private folder                                       | `visibility: private` on its folder note, or an empty `.private` file in it      |
| Never published (note)                               | `publish: false` or `draft: true`                                                |
| Never published (folder)                             | `publish: false` on its folder note, or an empty `.nopublish` file in the folder |

Folder rules cascade to all subfolders and cannot be overridden further down.

**Site notes and SEO**

Site-wide settings and authors live in the vault as notes with a `site:` key, so there is nothing to edit in code. The
starter kit has an example in `_site/` (with a `.nopublish` marker, so the notes never become pages):

```yaml
---
site: settings
title: My Garden
description: What this site is about.
url: https://example.com
image: share.png # default social image, raster ~1200x630
twitter: "@handle"
block-crawlers: [GPTBot] # optional robots.txt Disallow list
---
```

```yaml
---
site: author
name: Your Name
same-as: [https://github.com/you]
default: true # the default author
---
```

Several settings notes merge in vault-path order (later wins). The sync writes everything to `content/site.json`, which is
committed and public, so never put secrets in a site note. The site then generates `sitemap.xml`, `robots.txt`, RSS,
canonical URLs, social cards and JSON-LD (blog posts, authors, courses, breadcrumbs) on its own. You supply a good
`description` (about 150-160 characters), a raster `social-image` where a note deserves one, and `level`. The Writing
Guide's "Site notes" and "SEO" sections have the details.

**Courses**: a folder of numbered notes (`01 Basics.md`, `02 Next.md`) with a folder note `<folder>/<folder>.md` (or
`<folder>.md` beside it, or `<folder>/index.md`) carrying `title`, `description` and `cover`. It appears at
`/series/<folder>`; numbers set the order and are hidden from titles and URLs.

**Supported syntax**: wikilinks (`[[Note]]`, `[[Note|text]]`, `[[Note#Heading]]`), embeds (`![[image.png|300]]`),
callouts (with `-` / `+` to fold), Mermaid, fenced code with a language, footnotes, tables, task lists,
`==highlight==`, `$math$` and `$$math$$`. `%%comments%%` and block ids are stripped.

**Lesson endings**: course parts end with `## Summary` and `### Key takeaways` directly above the
`<- [[prev]] / [[Index]] / [[next]]` navigation line. Open a part with a `> [!summary] TL;DR` callout; it becomes the
description when the frontmatter has none.

**Copy the starter kit into your vault root:**

```sh
cp -r docs/vault-starter/. /path/to/vault/
```

That gives you `CLAUDE.md`, `_authoring/Writing Guide.md`, `_authoring/.nopublish` (so the guide is never
published), `_site/` (example site settings and author notes, never published) and `example-course/` to try the course
layout. Delete `example-course/` when you no longer need it.

## 6. Preview locally

```sh
pnpm sync
pnpm dev          # or: vp dev   -> http://localhost:3000
```

- `SHOW_PRIVATE=1 pnpm dev` also shows private notes. It only works in development
  (`NODE_ENV` other than `production`); a production build never shows them.
- `vp check` formats, lints and type checks. `vp test` runs the tests.
- Production build: `pnpm build`, then `pnpm start` (runs `node .output/server/index.mjs`, port from `PORT`, default
  3000).

## 7. Deploy to Vercel

1. **Push to GitHub** (public or private). Private notes are committed under `content/_private/` like any other
   note, so anyone who can read the repo can read them: treat "private" as "unlisted on the site", not as secret.
   Anything that must stay out of git entirely belongs in a `publish: false` note or a `.nopublish` folder. If you
   want private notes hidden from git readers too, keep the repo private.
2. In Vercel choose **Add New -> Project** and import the repo. `vercel.json` already sets `framework: null`, the
   install command (`corepack pnpm@12.15.0 install --frozen-lockfile`) and the build command, and Nitro detects Vercel
   by itself, so leave the dashboard defaults alone (if the framework preset dropdown shows up, pick **Other**).
3. Set your site's public origin so RSS, the sitemap, `robots.txt` and canonical links are absolute. The origin is
   the first of: the `SITE_URL` environment variable (for example `https://garden.example.com`), the `url` of your
   `site: settings` note (see "Site notes and SEO" in section 5), `VERCEL_PROJECT_PRODUCTION_URL`, then the request
   origin.

### Other hosts

Nitro chooses the target from `NITRO_PRESET` at build time. The app code does not change:

```sh
pnpm build && pnpm start                         # node-server (default) -> .output/server/index.mjs
NITRO_PRESET=bun pnpm build                      # then: bun .output/server/index.mjs
NITRO_PRESET=netlify pnpm build                  # auto-detected on Netlify
NITRO_PRESET=cloudflare_module pnpm build        # then: npx wrangler deploy
```

See https://nitro.build/deploy for all presets.

## 8. Day-to-day workflow

1. Write in Obsidian.
2. `pnpm sync` (or leave `pnpm sync:watch` running while you write, with `pnpm dev` for a live preview).
3. Commit the generated files and push:

   ```sh
   git add content public/attachments && git commit -m "sync vault" && git push
   ```

4. Vercel builds from the pushed repo and deploys.

## Troubleshooting

- **`note.md: attachment "x" is ambiguous, using a/x (also b/x)`**: the note references a bare file name that exists in
  several folders, none of them the note's own folder or an ancestor. The sync picks the closest one; use a path
  (`![[b/x.png]]`) or move the file next to the note. Same names in different folders are fine otherwise: each course
  can have its own `cover.svg`.
- **`attachment not found in vault: x (in note.md)`**: a note references a file the vault does not contain (check the
  name and extension).
- **Warning that `visibility: public` is ignored**: that note sits inside a private tree; folder rules cannot be
  overridden by a note.
- **A wikilink shows as plain text**: its target is missing, unpublished or private. Links resolve by filename
  (case-insensitive) or alias.
- **`N attachment(s) used only by private notes not published`**: `public/` is world-readable, so images used only by
  private notes are not copied. Use the image from a public note too if you need it.
- **Raw HTML in a `.md` note is not rendered**: use Markdown, or rename the note to `.mdx`.
- **Mermaid sequence diagram fails on `;`**: the site escapes `;` in sequence diagram message text for you. If another diagram
  fails to parse, check for `;` in its text first.
- **A cover or image does not show**: run `pnpm sync` (and commit `public/attachments/`); the build only sees
  committed copies.
- **`vault not found`**: set `OBSIDIAN_VAULT` to the right path.

## Using an AI writing assistant

The starter kit's `CLAUDE.md` tells Claude (or any agent that reads `CLAUDE.md`) to read
`_authoring/Writing Guide.md` before writing or editing a note, so it follows your frontmatter, visibility,
callout and course conventions. Open your vault folder in the assistant and ask it to draft notes. Keep the guide
in sync when you change your own conventions.
